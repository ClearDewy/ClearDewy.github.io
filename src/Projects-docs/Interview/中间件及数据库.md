# 中间件及数据库

## Mysql

### SQL基本语法、连接查询、分页查询，执行计划，慢查询日志

**SQL 基本语法**

- **数据查询（SELECT）**：

  - SELECT column1, column2 FROM table_name WHERE condition;

  - 用于从表中选取数据。

- **数据插入（INSERT）**：

  - INSERT INTO table_name (column1, column2) VALUES (value1, value2);

  - 用于向表中插入新数据。

- **数据更新（UPDATE）**：

  - UPDATE table_name SET column1 = value1, column2 = value2 WHERE condition;

  - 用于更新表中的数据。

- **数据删除（DELETE）**：

  - DELETE FROM table_name WHERE condition;

  - 用于从表中删除数据。

**连接查询**

连接查询用于结合来自两个或多个表的行。

- **内连接（INNER JOIN）**：

  - SELECT columns FROM table1 INNER JOIN table2 ON table1.column = table2.column;

  - 只返回两个表中匹配的行。

- **左连接（LEFT JOIN）**：

  - SELECT columns FROM table1 LEFT JOIN table2 ON table1.column = table2.column;

  - 返回左表所有行，即使右表中没有匹配。

- **右连接（RIGHT JOIN）**：
  - SELECT columns FROM table1 RIGHT JOIN table2 ON table1.column = table2.column;
  - 类似于左连接，但返回右表的所有行。

**分页查询**

分页查询用于返回查询结果的一部分。

- SELECT columns FROM table LIMIT offset, count;
- LIMIT 指定返回记录的数量，offset 指定返回记录的起始位置。

**执行计划**

执行计划用于分析 SQL 语句的执行过程。

- 通过 EXPLAIN 关键字可以查看 MySQL 是如何处理你的 SQL 语句的。
- EXPLAIN SELECT columns FROM table WHERE condition;

**慢查询日志**

慢查询日志用于记录执行时间超过指定阈值的查询。

- **启用慢查询日志**：
  - 在 MySQL 配置文件中设置 slow_query_log = 1 来启用慢查询日志。
  - 设置 long_query_time 来指定查询执行时间的阈值。
- **分析慢查询日志**：
  - 慢查询日志记录了查询的 SQL 语句和执行时间，可以用来分析和优化慢查询。

### 存储引擎，文件结构，行记录格式，缓冲池

**存储引擎**

MySQL 支持多种存储引擎，每种存储引擎都有自己的特点和适用场景：

- **InnoDB**：

  - 默认的存储引擎，提供了事务支持、行级锁定和外键约束。

  - 支持 ACID（原子性、一致性、隔离性、持久性）事务。

  - 适用于需要高可靠性和事务处理的应用。

- **MyISAM**：

  - 早期的默认存储引擎，不支持事务和行级锁定。

  - 高速读取操作，但写入操作会锁定整个表。

  - 适用于读密集型应用。

- **其他引擎**（如 Memory、Archive）：
  - 用于特定需求，如 Memory 提供内存中的数据存储，适用于临时数据

**文件结构**

MySQL 的数据存储在文件系统中，其文件结构取决于所使用的存储引擎：

- **InnoDB**：
  - .ibd：每个表的数据和索引存储在单独的文件中（如果启用了文件分表）。
  - ibdata：如果没有启用文件分表，所有表的数据和索引存储在共享表空间中。
  - ib_logfile：重做日志文件，用于事务的持久性和恢复。
- **MyISAM**：
  - .MYD（MyISAM Data）：存储表数据。
  - .MYI（MyISAM Index）：存储索引信息。
  - .frm：存储表结构。

**行记录格式**

行记录格式决定了表中行数据的存储方式。InnoDB 支持多种行格式，如 COMPACT、REDUNDANT、DYNAMIC 和 COMPRESSED：

- **REDUNDANT**

  - **特点**：
    - 这是 InnoDB 最早的行格式。
    - 每个行记录包含一些额外的信息，如行头信息。
    - 不太高效，尤其是对于空间的占用。

  - **适用场景**：
    - 主要用于旧版本的 MySQL 兼容性。

- **COMPACT**

  - **特点**：
    - 相比于 REDUNDANT，COMPACT 行格式减少了行记录的额外信息，例如，它使用较少的字节来存储列的长度。
    - 提高了空间利用率，减少了不必要的存储开销。

  - **适用场景**：
    - 对于大多数现代应用来说，是一个更好的选择，特别是当表中包含很多可变长度字段（如 VARCHAR）时。

- **DYNAMIC**

  - **特点**：
    - 为了进一步优化存储效率，DYNAMIC 行格式支持将可变长度列（如 BLOB、TEXT）的长部分存储在溢出页中，而不是主数据页中。
    - 提高了对于大型字段的存储效率。

  - **适用场景**：
    - 当表包含大量 BLOB 或 TEXT 字段时，DYNAMIC 行格式特别有用。

- **COMPRESSED**

  - **特点**：
    - COMPRESSED 行格式在 DYNAMIC 的基础上添加了对数据的压缩支持。
    - 可以显著减少磁盘空间占用，但可能增加 CPU 负担（由于压缩和解压缩操作）。

  - **适用场景**：
    - 对于磁盘空间使用敏感或数据量非常大的应用，尤其是只读或查询多于更新的场景。

**缓冲池**

- **缓冲池的作用**

  缓冲池主要用于减少数据库操作的磁盘 I/O 成本。它做到这一点的方式是：

  - **缓存数据页**：当数据被读取时，它被放置在缓冲池中。后续对这些数据的读取可以直接从内存中完成，而不需要再次访问磁盘。

  - **缓存索引页**：索引页也被缓存在内存中，加快索引查找和数据检索。

  - **写回机制**：对数据的修改首先在内存中进行，然后定期以及在需要时写回到磁盘。这种方式称为“延迟写回”或“异步写回”。

- **缓冲池的管理**

  - **大小配置**：缓冲池的大小是性能调优中的关键因素。一般建议将其设置为系统内存的 50% 到 80%，但具体取决于系统的总内存和其他应用程序的内存需求。

  - **多实例**：在高负载的系统中，可以配置多个缓冲池实例，以减少线程竞争和提高并发性能。

  - **页替换策略**：InnoDB 使用 LRU（最近最少使用）算法管理缓冲池中的页，以确保经常访问的数据留在缓冲池中。

- **缓冲池的性能影响**

  - **命中率**：缓冲池的命中率是衡量其性能的关键指标。高命中率意味着大多数数据读取可以直接从内存完成。

  - **脏页处理**：脏页是指已经修改但还未写回磁盘的页。InnoDB 定期将脏页刷新到磁盘，以保证数据的一致性和持久性。

  - **内存压力**：如果缓冲池太小，可能导致频繁的页交换，增加 I/O 开销。如果太大，则可能会影响系统的其他部分。

- **监控和调优**

  - **性能监控**：通过性能监控工具（如 SHOW ENGINE INNODB STATUS）可以查看缓冲池的状态和性能指标。

  - **动态调整**：在 MySQL 5.7 及以上版本中，可以在运行时动态调整缓冲池的大小，这为性能调优提供了更大的灵活性。

### 索引

在数据库系统中，索引是一种优化查询速度的数据结构。它们在数据库表中创建一个额外的数据结构，以快速定位数据。讨论索引通常指的是 B-Tree 索引和哈希索引，这两种是最常见的索引类型。

#### 索引结构，优缺点

- **B-Tree 索引（通常为B+树）**

  - **结构**：

    - B-Tree（平衡树）索引是一种自平衡树结构，它保持数据有序，并允许搜索、顺序访问、插入和删除操作在对数时间内进行。

    - 在 B-Tree 结构中，所有叶子节点都在同一层，数据按顺序存储。

  - **优点**：

    - **多用途**：适用于各种类型的查询，包括等值查询、范围查询和排序操作。

    - **有序性**：支持顺序读取，对于范围查找和排序尤其有效。

    - **动态性**：在数据插入和删除时，B-Tree 能自动保持平衡。

  - **缺点**：

    - **空间占用**：相比于其他索引类型，B-Tree 可能占用更多的空间。

    - **维护成本**：对数据进行更新（插入、删除）时，维护 B-Tree 的成本比哈希索引高。

- **哈希索引**

  - **结构**：

    - 哈希索引基于哈希表实现，它使用哈希函数将键值映射到表中的一个位置来快速检索数据。

    - 通常只用于等值比较查询。

  - **优点**：

    - **快速查找**：对于等值查询，提供极快的访问时间。

    - **空间效率**：一般来说，哈希索引比 B-Tree 占用更少的空间。

  - **缺点**：

    - **不支持范围查询**：由于数据不是有序存储的，哈希索引不适合范围查询。

    - **无序性**：不支持按顺序访问数据，因此不适合排序操作。

    - **哈希冲突**：当多个键哈希到同一个值时，会发生哈希冲突，影响性能。

**其他索引类型**

- **全文索引**：用于文本数据的搜索，如 MySQL 的 FULLTEXT 索引。
- **空间索引**：用于地理空间数据，如 MySQL 的 R-Tree 索引。

**索引的选择**

在选择索引类型时，需要考虑数据的特性和查询的类型：

- B-Tree 索引是最通用的类型，适用于大多数场景。
- 哈希索引适用于快速等值查找，但不适合范围查找或排序。
- 特殊类型的数据（如文本或地理空间数据）可能需要专门的索引类型。

#### 索引分类

- **按数据结构分类**

  - **B-Tree 索引**：最常见的索引类型，适用于大多数查询类型，包括范围查询和精确匹配。

  - **B+Tree 索引**：在 B-Tree 的基础上进行了优化，更适合于读密集的数据库操作。

  - **哈希索引**：基于哈希表实现，适用于快速精确匹配查询，但不适用于范围查询。
  - **位图索引**：使用位图来表示索引键和行的关系，适用于具有低基数（即重复值较多）的列。

  - **R-Tree 索引**：用于空间数据，如地理信息系统中。

  - **全文索引**：用于文本搜索，如 MySQL 的 FULLTEXT 索引。

- **按功能分类**

  - **主键索引**：每个表的主键自动创建的索引。

  - **唯一索引**：确保列中每个值的唯一性。

  - **复合索引**：一个索引包含多个列。

  - **部分索引**：索引仅包含表中的一部分行。

  - **覆盖索引**：索引包含了查询中需要的所有数据，避免了访问表数据。

- **按应用方式分类**

  - **单列索引**：只基于单个列建立的索引。

  - **多列索引**：基于多个列联合建立的索引，其中列的顺序非常重要。

  - **外键索引**：在外键约束的列上自动或手动创建的索引，用于提高关联查询的性能。

  - **聚簇索引**：表中数据的物理存储顺序与索引的顺序相同，一般在主键上实现。

#### 索引引用，索引失效

索引引用（即何时何地索引被有效使用）和索引失效（即索引无法被查询优化器利用的情况）。

**索引引用**

一个数据库查询在以下情况下会有效地使用索引：

- **精确匹配**：在 WHERE 子句中对索引列进行精确匹配。

- **范围查询**：对索引列进行范围查找，如使用 <, <=, >, >=。

- **排序和分组**：在 ORDER BY 或 GROUP BY 子句中使用索引列。

- **覆盖索引**：当查询列仅包含索引中的字段时，即所谓的覆盖索引。

- **连接操作**：在 JOIN 操作中使用索引列作为连接条件。

**索引失效**

索引可能因为以下原因失效，即查询无法利用索引：

- **列转换**：在索引列上进行函数或类型转换，如 WHERE YEAR(date_column) = 2021。

- **不适当的运算符**：使用某些运算符可能导致索引失效，如 NOT, <>, OR（在某些条件下）。

- **复合索引顺序**：在复合索引中，如果查询条件不包括索引列的最左前缀，则索引可能不被使用。必须从索引定义的最左边的列开始使用索引，才能保证索引被有效利用。

- **LIKE 操作符**：使用 LIKE 时以通配符开头的字符串，如 LIKE '%abc'。

- **非 SARGable 查询**：不可搜索参数的查询，即无法有效利用索引的查询。

- **数据分布和选择性**：当索引列的值非常分散或高度重复时，查询优化器可能决定不使用索引。

#### 磁盘存储结构

磁盘存储结构是指如何在磁盘上有效地组织、存储和管理数据。这涉及到数据文件的布局、数据访问方法和数据索引结构等。

**数据文件**

数据库的数据通常存储在磁盘上的数据文件中。这些文件的类型和结构取决于具体的数据库系统：

- **表数据文件**：

  存储实际的表数据，包括行记录。在关系型数据库中，一个表可以对应一个文件，或多个表共享一个文件。

- **索引文件**：

  - 存储数据库索引，用于加快数据检索速度。

  - 索引文件通常与表数据文件分开，以优化读写性能。

**页（Pages）**

- **数据页**：

  - 数据库的基本存储和I/O单位。

  - 包含表中的行数据或索引数据。

  - 一般大小固定，如 4KB、8KB 或更大。

- **管理信息**：
  - 每个数据页包含管理信息，如页头信息，记录数据在页内的位置。

**磁盘块和I/O**

- 数据库系统通常按页进行磁盘I/O操作，这意味着即使只需访问一页中的少量数据，整个页也会被加载到内存。

**文件组织和访问方法**

- **堆（Heap）文件组织**：

  - 数据按插入顺序存储，没有特定顺序。

  - 适用于没有特定排序需求的场景。

- **顺序（Sequential）文件组织**：

  - 数据按某个键的值排序存储。

  - 适用于需要大量范围查询的场景。

- **散列（Hashed）文件组织**：

  - 使用哈希技术将数据分散存储。

  - 适用于快速等值查找。

**日志文件**

- 记录数据库操作的日志，用于恢复和故障转移。
- 包括事务日志、审计日志等。

### 并发控制

#### 事务

##### 1、ACID：可用性（原子性），一致性，隔离性，持久性

- **原子性（Atomicity）**：

  - 事务中的操作要么全部完成，要么全部不执行。

  - 确保操作不会因为系统错误而只完成一部分。

- **一致性（Consistency）**：

  - 事务必须将数据库从一个一致性状态转换到另一个一致性状态（合法的状态）。

  - 一致性规则由业务逻辑定义（如账户余额不可为负）。

- **隔离性（Isolation）**：

  - 确保并发事务的操作互不干扰，事务之间相互独立。

  - 隔离级别的设置会影响隔离性的实现。

- **持久性（Durability）**：
  - 一旦事务提交，其结果就永久保存在数据库中，即使系统发生故障也不会丢失。

#### 隔离级别

##### 1、读未提交，读已提交，可重复读，可串行化

隔离级别定义了一个事务可能必须隔离其他事务的程度，不同的隔离级别会导致不同程度的影响，包括并发性能和可能遇到的并发问题（如脏读、不可重复读、幻读）。

- **读未提交（Read Uncommitted）**：

  - 允许事务读取未提交的更改。

  - 可能导致脏读、不可重复读和幻读。

- **读已提交（Read Committed）**：

  - 一个事务只能读取已经提交的更改。

  - 可以防止脏读，但不可重复读和幻读仍可能发生。

- **可重复读（Repeatable Read）**：

  - 在事务开始时读取的数据在事务期间始终保持一致。

  - 防止脏读和不可重复读，但幻读可能发生。

- **串行化（Serializable）**：

  - 最高的隔离级别，事务完全串行执行。

  - 防止脏读、不可重复读和幻读，但并发性能最差。

##### 2、并发访问问题：脏读，幻读，不可重复读

这些问题通常与事务的隔离级别有关，隔离级别越低，这些问题出现的可能性越大。

- **脏读（Dirty Read）**

  - **定义**：脏读发生在一个事务读取了另一个事务未提交的数据。如果那个事务失败并回滚，那么第一个事务读取的数据就是不正确的。

  - **示例**：事务 1 读取了事务 2 修改但尚未提交的数据。如果事务 2 回滚，事务 1 就读取了“脏”的数据。

  - **隔离级别**：在“读未提交”（Read Uncommitted）级别下，脏读是可能发生的。

- **不可重复读（Non-repeatable Read）**

  - **定义**：不可重复读发生在一个事务读取了同一数据两次，并且两次读取的结果不同，这是因为另一个事务在两次读取之间修改了数据并提交。

  - **示例**：事务 1 读取了一行数据，事务 2 修改了那行数据并提交。当事务 1 再次读取同一行数据时，会发现数据已经改变。

  - **隔离级别**：在“读已提交”（Read Committed）级别下，可以避免脏读，但不可重复读仍然可能发生。

- **幻读（Phantom Read）**

  - **定义**：幻读与不可重复读类似，但区别在于幻读涉及到由其他事务插入或删除的新行。即一个事务两次执行相同的查询，第二次查询返回了不同的行。

  - **示例**：事务 1 根据某个条件查询得到一组行，事务 2 在此期间插入了一些新的符合那个条件的行并提交。当事务 1 再次执行相同的查询时，会发现有额外的“幻影”行。

  - **隔离级别**：在“可重复读”（Repeatable Read）级别下，可以避免脏读和不可重复读，但幻读仍可能发生。只有在“串行化”（Serializable）级别下，才能完全避免所有这三种问题。

#### 锁

##### 锁类型

###### 1、表锁：全局锁，元数据锁，意向锁

表锁是一种粗粒度锁，它在整个表上放置锁。

- **全局锁**：

  - 影响数据库中所有表的锁。例如，在做全库备份时可能会使用全局锁。

  - 在 MySQL 中，可以使用 FLUSH TABLES WITH READ LOCK 命令来实现全局锁。

- **元数据锁（Metadata Lock, MDL）**：

  - 当访问一个表的结构（如进行查询或修改表结构）时，数据库会自动使用元数据锁来保护表的元数据不被同时修改。

  - 用于保证读写的一致性和完整性。

- **意向锁**：

  - 意向锁是一种特殊类型的表锁，用来表明事务对给定表中的行加了哪种类型的行锁（共享或排他）。

  - 在 InnoDB 中，意向锁是一种内部机制，用于在行级锁之前加锁。

###### 2、行锁：记录锁，间隙锁，临键锁

行锁是一种细粒度锁，仅锁定被事务访问的特定行。

- **记录锁**：
  - 直接锁定目标行。如果一个事务修改了一行数据，其他事务就无法修改这一行，直到第一个事务提交或回滚。

- **间隙锁（Gap Lock）**：

  - 锁定一个范围，但不包括记录本身，主要用于防止幻读。

  - 例如，在范围查询中，间隙锁可以锁定一个区间，防止其他事务插入新行。

- **临键锁（Next-Key Lock）**：

  - 是记录锁和间隙锁的组合，锁定一个范围和范围内的行。

  - 这种锁机制在可重复读（Repeatable Read）隔离级别下用于防止幻读。

##### 加锁时机，释放时机

**加锁时机**

- **事务开始时**：

  - 当一个事务开始执行操作（如读取或修改数据）时，它需要在所涉及的数据上加锁以维护一致性和隔离性。

  - 在某些数据库系统中，例如在 MySQL 的 InnoDB 存储引擎中，锁是自动加上的，无需手动干预。

- **根据隔离级别自动加锁**：
  - 不同的隔离级别会影响加锁的行为。例如，在“可重复读”隔离级别下，读取操作可能会触发行锁或间隙锁。

- **显式锁定**：
  - 在一些情况下，可以显式地请求锁定某些数据。例如，SQL 提供了 LOCK TABLES 语句用于显式地对表加锁。

- **查询优化**：
  - 数据库查询优化器会根据查询的类型和数据的访问模式自动决定加锁的策略，以最小化锁的影响。

**释放锁时机**

- **事务结束时**：

  - 当事务提交或回滚时，所有由该事务持有的锁都会被释放。

  - 这是确保事务完整性的一个关键步骤。

- **表级锁的释放**：
  - 对于显式加的表级锁（如使用 LOCK TABLES），需要使用 UNLOCK TABLES 显式释放锁。

- **自动释放**：
  - 在大多数现代数据库系统中，锁的管理是自动的，锁会在适当的时候自动释放，无需手动干预。

- **锁升级和降级**：
  - 在一些复杂的事务中，锁可能会根据需要进行升级（如从行锁升级到表锁）或降级。这些操作通常由数据库系统自动管理。

**注意事项**

- **避免长事务**：长事务持有锁的时间较长，可能会导致锁争用和性能问题。
- **避免死锁**：在并发事务中，不当的锁使用可能导致死锁。大多数数据库系统提供了死锁检测和解决机制。
- **谨慎使用显式锁定**：过度使用显式锁定可能会降低并发性能。

##### 死锁问题，解决方案

**死锁的产生**

- **循环等待**：两个或多个事务互相持有对方需要的锁。

- **资源持有和等待**：一个事务持有资源的同时等待其他资源。

- **不可剥夺条件**：一旦资源被事务持有，其他事务不能强制剥夺。

- **并行执行**：事务以不同的顺序访问资源。

**解决死锁的方案**

- **预防死锁**：

  - **顺序访问资源**：确保所有事务按照相同的顺序申请资源。

  - **超时机制**：为事务的锁定操作设置超时时间。

- **避免死锁**：

  - **资源分配图**：使用资源分配图来动态检查是否会发生循环等待。

  - **事务优先级**：基于优先级分配资源，避免低优先级事务持有高优先级事务需要的资源。

- **检测与恢复**：

  - **死锁检测**：数据库系统周期性地检测死锁的存在。

  - **事务回滚**：当检测到死锁时，选择并回滚某些事务以解锁。

- **使用行级锁**：
  - 尽量使用行级锁，它比表级锁更细粒度，减少了死锁的可能性。

- **优化事务设计**：
  - 减少事务的大小和持续时间，避免复杂的事务操作。

- **并发控制**：
  - 使用乐观并发控制（OCC）或悲观并发控制（PCC），根据应用的特点选择合适的并发控制策略。

**OCC与PCC**

- **乐观并发控制（OCC）**

  乐观并发控制基于这样一个假设：冲突发生的几率很低，因此在大多数时间里，事务可以在没有显著数据库锁定的情况下进行。

  - **工作流程**：

    - **开始**：在事务开始时记录一个时间戳或版本号。

    - **修改**：进行数据读取和修改，但不立即写入数据库。

    - **提交前验证**：在事务提交前，检查自事务开始以来是否有其他事务修改了相关数据。

    - **提交/回滚**：如果没有冲突，事务提交更改；如果有冲突，事务回滚。

  - **适用场景**：乐观并发控制适用于读操作多于写操作的应用场景，即在大多数情况下，事务不会试图修改相同数据的环境。

- **悲观并发控制（PCC）**

  悲观并发控制是一种基于锁机制的方法，它假设冲突是常见的，因此在读取或修改数据时应采取谨慎态度。

  - **工作流程**：

    - **锁定**：在读取或修改数据之前，事务首先对所需数据加锁。

    - **处理**：执行所需的读取或更新操作。

    - **释放锁定**：操作完成后，事务释放其持有的锁。

    - **提交/回滚**：根据操作结果，事务提交或回滚。

  - **适用场景**：悲观并发控制适用于写操作比读操作频繁的应用场景，尤其是在高冲突环境中。

- **OCC 与 PCC 的比较**

  - **资源消耗**：OCC 通常消耗较少资源，因为它减少了锁的使用。而 PCC 可能导致更高的锁定开销。

  - **冲突处理**：OCC 在冲突发生时采取回滚，而 PCC 通过锁预防冲突的发生。

  - **性能影响**：在高冲突的应用中，OCC 可能导致较多的回滚，而 PCC 则可能导致锁争用和死锁。

#### MVCC

多版本并发控制（MVCC, Multi-Version Concurrency Control）是一种在数据库系统中广泛使用的并发控制技术。它通过为每个读取的数据创建版本（快照）来允许多个事务同时对同一数据进行操作，而不会相互干扰。

##### 1、transaction_id（事务id）

- 每个事务在开始时都会被分配一个唯一的事务ID（transaction_id）。
- 这个ID不仅标识了事务，还用于记录每个数据版本是由哪个事务创建的。
- 在 MVCC 中，事务ID帮助数据库确定在任何给定时间哪些数据版本对特定事务是可见的。

##### 2、roll_pointer（回滚指针）

- Roll pointer 是一个指向数据的旧版本的指针，用于实现版本链。
- 当更新数据时，新版本的记录会包含一个指向旧版本记录的 roll pointer。
- 这允许数据库在需要时回滚到旧版本，如事务回滚或为早期的事务读取数据版本。

##### 3、read_view（读视图）

- Read view 是在事务开始时创建的一个逻辑视图，它包含了该事务可以看到的数据版本。
- 读视图确定了事务开始时数据库中活跃的其他事务，以及哪些数据版本对当前事务是可见的。
- 它基于其他事务的事务ID和数据版本来决定当前事务可见的数据。

**MVCC 的工作原理**

- 当事务读取数据时，它会基于其 read view 来获取对应的数据版本。

- 如果一个事务需要更新数据，它会创建一个新的数据版本，并将 transaction_id 设置为自己的ID，同时保留 roll pointer 指向旧版本。

- 其他事务根据自己的 read view 来获取它们可以看到的数据版本。

**MVCC 的优势**

- **减少锁的需求**：通过允许多个事务并发读取同一数据的不同版本，MVCC 减少了锁的需求，从而提高了并发性能。
- **避免写写冲突**：事务在更新数据时不会相互影响，因为它们操作的是不同的数据版本。
- **非阻塞读**：读操作通常不需要锁定资源，因为它们读取的是数据的快照。

### 日志

#### 日志类型

##### 1、bin log（二进制日志）、undo log （回滚日志），redo log（重做日志）

- **二进制日志（Binlog）**

  - **功能**：二进制日志记录了所有修改数据库数据的语句（如 INSERT、UPDATE、DELETE），以及数据库结构变化的语句（如 CREATE TABLE、ALTER TABLE）。

  - **用途**：
    - **数据复制**：用于主从复制，主服务器上的二进制日志被用来在从服务器上重放这些操作。
    - **数据恢复**：在灾难恢复时，二进制日志可以用来重放数据变更，恢复数据库状态。

  - **特点**：
    - 记录的是逻辑变更，而非物理变更。
    - 可以被设置为每个事务提交时刷新到磁盘，以提高数据的持久性。

- **回滚日志（Undo Log）**

  - **功能**：回滚日志记录了数据的旧版本信息，用于在事务回滚时恢复数据到事务开始前的状态。

  - **用途**：
    - **事务管理**：支持事务的 ACID 属性，特别是原子性（Atomicity）和一致性（Consistency）。
    - **MVCC**：支持多版本并发控制，允许读事务访问数据的旧版本。

  - **特点**：
    - 记录在事务开始之前数据的状态。
    - 事务提交后，相关的回滚信息会被清除。

- **重做日志（Redo Log）**

  - **功能**：重做日志记录了对数据的修改操作，但与二进制日志不同，它记录的是物理层面的变更。

  - **用途**：
    - **数据恢复**：在系统崩溃或宕机后，重做日志用于恢复提交的事务所做的修改。

  - **特点**：
    - 是 InnoDB 存储引擎特有的日志。
    - 以循环方式写入，分为一组固定大小的文件。
    - 通常每个事务的修改在提交时被写入重做日志。

#### 作用：灾备、崩溃恢复、事务回滚、主从同步等

#### 存储格式，写入格式，刷盘时机/频率

- **日志的存储格式**

  - **物理日志**：

    - 以物理格式存储，记录数据页或记录的具体字节级变化。

    - 例如，InnoDB 的重做日志（redo log）就是一种物理日志。

  - **逻辑日志**：

    - 以逻辑格式存储，记录高层次的数据操作，如 SQL 语句。

    - 例如，MySQL 的二进制日志（binlog）记录的是逻辑日志。

- **日志的写入格式**

  - **顺序写入**：
    - 日志通常以顺序的方式写入，这种方式减少了磁盘I/O的寻道时间，提高了写入效率。

  - **批量写入**：
    - 日志条目可能在内存中积累并作为一个批量写入磁盘，以提高性能。

- **刷盘时机/频率**

  - **同步刷盘**：在每次事务提交时立即刷盘，确保了事务的持久性和一致性。但这种方式可能影响性能，因为它增加了每个事务的I/O开销。

  - **异步刷盘**：日志信息先在内存中积累，然后在特定的时机批量写入磁盘。这可以提高性能，但在系统崩溃的情况下可能导致最近的一些事务丢失。

  - **基于时间间隔的刷盘**：日志按固定的时间间隔刷写到磁盘，例如，每几秒钟刷写一次。

  - **基于日志大小的刷盘**：当累积的日志达到一定大小时触发刷盘操作。

- **配置的重要性**

  - **性能与可靠性的平衡**：配置刷盘策略时需要在性能和数据可靠性之间做出权衡。例如，金融交易系统可能需要更高的数据可靠性，而对性能要求稍低。

  - **应用场景**：不同的应用场景对日志的需求不同。事务密集型应用可能需要更频繁的日志刷盘，而查询密集型应用可能对日志刷盘的频率要求不那么高。

### 主从切换/复制/同步，读写分离，分库分表

- **主从切换/复制/同步**

  - **主从复制**：在这种架构中，数据从一个主数据库自动复制到一个或多个从数据库。主数据库处理写操作，而从数据库处理读操作。这样可以分散读取负载。

  - **主从同步**：同步过程确保主数据库中的更改实时或准实时地反映在从数据库中。同步机制通常涉及日志文件的复制和重放。

  - **主从切换**（故障转移）：如果主数据库发生故障，系统会将一个从数据库升级为新的主数据库，以保持服务的连续性。这个过程可以是自动的，也可以是手动的。

  - **读写分离**：**读写分离**指的是将数据库的读操作和写操作分离到不同的服务器上。主数据库负责处理写操作和事务性操作，而从数据库负责处理读操作，如查询。这样做可以显著提高数据库的性能和扩展性，因为它减轻了主数据库的负载，并允许更有效地利用从数据库。

- **分库分表**

  - **分库**（数据库分片）：

    - 将数据分布在多个数据库（或数据库实例）上。

    - 这通常用于大型应用，可以水平扩展数据库架构。

  - **分表**：

    - 将大型表分解成多个小表。这可以是垂直分表（按列分）或水平分表（按行分，也称为分区）。

    - 分表有助于管理大数据集，提高查询效率和数据维护。

- **实施考虑因素**

  - 在实施这些策略时，需要考虑数据一致性、复制延迟、系统复杂性和维护成本。

  - 需要确保应用程序能够正确处理读写分离，并且能够在主从切换时保持稳定运行。

  - 分库分表策略需要仔细规划，以确保数据分布均匀，避免数据倾斜问题。

## NoSQL

### redis

#### 数据类型

##### 1、基础数据类型

- **字符串（String）**

  - 最基本的数据类型。

  - 可以包含任何数据，比如文本、数字或二进制数据。

  - 用于缓存、计数、共享会话等。

- **列表（List）**

  - 字符串元素的有序集合，按插入顺序排序。

  - 可以在列表的头部或尾部添加元素。

  - 适用于消息队列、最近访问的项目等。

- **集合（Set）**

  - 字符串元素的无序集合，且不允许重复。

  - 提供诸如交集、并集、差集等操作。

  - 适用于无序集合存储、去重等。

- **有序集合（Sorted Set）**

  - 与集合类似，但每个元素都会关联一个双精度浮点数分数。

  - 元素按分数有序排列，分数可以重复，但成员必须唯一。

  - 适用于排行榜、带优先级的队列等。

- **哈希（Hash）**

  - 键值对集合，类似于 Java 的 HashMap 或 Python 的字典。

  - 适合存储对象（比如用户信息）。

- **位图（Bitmap）**

  - 使用字符串作为底层表示，实际上是对字节串的位操作。

  - 可以用于实现高效的计数器、标记等。

- **HyperLogLog**

  - 一种基于概率的数据结构，用于高效地估计集合中元素的基数（比如独特元素的数量）。

  - 适合用于大规模数据集的去重计数。

##### 2、底层编码方式

Redis 的不同数据类型在底层有着不同的编码方式，这些编码方式是 Redis 优化内存使用和性能的关键。

- **字符串（String）**
  - **int**：当字符串值可以表示为整数时，Redis 会使用 int 编码来节省空间。
  - **embstr**：对于小于等于 44 字节的字符串，使用 embstr 编码，这种编码方式将字符串数据和 Redis 对象存储在连续的内存空间中。
  - **raw**：对于大于 44 字节的字符串，使用 raw 编码，这种方式将字符串数据和 Redis 对象分开存储。

- **列表（List）**

  - **ziplist**：当列表中的所有字符串元素都较小（小于某个阈值），且列表长度较短时，Redis 使用 ziplist 编码来节省内存。

  - **linkedlist**：对于较大的元素或较长的列表，Redis 使用传统的 linkedlist 编码。

- **集合（Set）**

  - **intset**：当集合只包含整数元素且数量较少时，使用 intset 编码，这是一个紧凑的数组结构。

  - **hashtable**：对于较大的集合或包含非整数的集合，使用 hashtable 编码。

- **有序集合（Sorted Set）**

  - **ziplist**：对于元素数量少且元素大小小的有序集合，Redis 使用 ziplist 编码。

  - **skiplist**：对于较大的有序集合，Redis 使用跳跃表（skiplist）和哈希表的组合来存储元素和分数。

- **哈希（Hash）**

  - **ziplist**：小型哈希（即键值对数量少，且键值对长度短）使用 ziplist 编码。

  - **hashtable**：大型哈希使用 hashtable 编码。

**特别注意**

- 这些编码方式是为了优化内存使用和提高性能。例如，ziplist 编码将多个元素紧凑地存储在一块连续的内存区域，从而减少了内存占用，但它可能在元素访问和修改上不如其他编码方式高效。
- Redis 会根据操作动态地改变对象的编码方式。例如，当你往一个使用 ziplist 编码的列表中添加足够多的元素，使其超过了某个阈值，Redis 会将其编码方式从 ziplist 转变为 linkedlist。

#### 使用场景

##### 1、常见数据类型使用，布隆过滤器，分布式锁等

**常见数据类型的使用场景**

- **字符串（String）**：

  - 缓存数据，如网页、查询结果等。

  - 存储临时数据，如会话、令牌等。

  - 计数器，如网页访问次数。

- **列表（List）**：

  - 实现队列或堆栈，支持消息队列和任务队列。

  - 存储有序数据，如用户的最新消息等。

- **集合（Set）**：

  - 去重，如统计独立访客数。

  - 社交网络中的好友列表、共同好友等。

- **有序集合（Sorted Set）**：

  - 排行榜，如游戏分数排名。

  - 时间序列数据，如股票价格。

- **哈希（Hash）**：

  - 存储对象或实体，如用户的个人信息。

  - 存储键值对的集合，如配置项。

**布隆过滤器（Bloom Filter）**

布隆过滤器（Bloom Filter）是一种空间效率很高的概率型数据结构，用于测试一个元素是否是一个集合的成员。它在判断不存在时非常准确，但在判断存在时可能会有误判（即假阳性）。布隆过滤器常用于那些不需要完全准确的场景，如网络应用中的缓存层或数据库索引。

- **工作原理**

  布隆过滤器通过多个不同的哈希函数来检测元素是否存在于集合中：

  - **初始化**：初始化一个长度为 m 的比特数组，所有位初始值为 0。

  - **添加元素**：对于集合中的每个元素，使用 k 个不同的哈希函数对其进行哈希，并将结果映射到比特数组的 m 位上。将这些位设置为 1。

  - **检查元素**：对于要检查的元素，同样使用这 k 个哈希函数进行哈希，并映射到比特数组。如果所有映射的位都是 1，布隆过滤器报告该元素“可能存在”于集合中。如果任何一位是 0，布隆过滤器报告该元素“绝对不在”集合中。

- **特点和用途**

  - **空间效率和查询时间**：相比于其他数据结构，布隆过滤器更加空间有效，且查询时间几乎是常数。

  - **误判率**：布隆过滤器可能会错误地判断某个不存在的元素为存在（假阳性），但不会将存在的元素判断为不存在（假阴性）。

  - **不可删除**：传统的布隆过滤器不支持从集合中删除元素，因为它会影响其他元素的判断。

  - **应用场景**：

    - 网络应用中的快速集合查询，例如网页爬虫的链接检测、数据库查询缓存。

    - 防止缓存穿透，减少对数据库的无效查询。

    - 数据同步，快速检查数据是否存在于远程集合中。

  - **实现注意事项**

    - **哈希函数的选择**：需要选择好的哈希函数以避免太多的哈希冲突。

    - **大小和误判率的权衡**：增加比特数组的大小可以减少误判率，但会占用更多空间。

    - **调整参数**：根据预期存储的元素数量和可接受的误判率来调整比特数组的大小和哈希函数的数量。

**分布式锁**

Redis 分布式锁是一种在分布式系统中用于同步多个进程或服务访问共享资源的机制。使用 Redis 实现分布式锁主要是因为其高性能和内置的过期机制。这种锁通常用于确保在一个时间点只有一个进程可以执行特定的操作或访问特定的资源。

- **基本原理**

  - **锁的创建**：

    - 使用 Redis 的 SET 命令与 NX（Not eXists）和 EX（Expire）选项来实现锁的创建。

    - NX 确保只有当锁不存在时才设置锁，实现互斥。

    - EX 设置锁的过期时间，防止死锁。

  - **锁的释放**：

    - 当任务完成后，通过删除对应的 Redis 键来释放锁。

    - 通常使用 Lua 脚本来确保检查和删除操作的原子性。

  - **处理锁的过期**：

    - 锁的过期时间（TTL）应该足够长，以覆盖被锁保护的代码的执行时间。

    - 如果一个进程持有锁的时间超过了过期时间，锁将被自动释放，这样可以防止因进程崩溃或其他原因导致的死锁。

- **实现步骤**

  - **尝试获取锁**：

    - 进程尝试通过执行 SET 命令来获取锁。

    - 如果返回值为 1（或 OK），则表示成功获取锁。

  - **执行代码**：
    - 获取锁后，进程执行其需要同步的操作。

  - **释放锁**：
    - 完成操作后，进程应立即释放锁，以便其他进程可以获取。

- **安全性考虑**

  - **确保锁的唯一性**：
    - 锁的键应该是唯一的，以避免不同的操作或资源间的冲突。

  - **避免错误释放锁**：
    - 确保只有锁的持有者能够释放它。这通常通过在锁中存储一个唯一的值（如 UUID 或线程ID）来实现。

  - **处理锁的续命**：
    - 对于长时间运行的任务，需要考虑在任务执行期间定期续命（重新设置锁的过期时间）。

- **使用场景和局限性**

  - Redis 分布式锁适用于需要跨多个进程或服务器同步访问共享资源的场景。

  - 它的局限性在于依赖于 Redis 实例的可用性和网络延迟。如果 Redis 实例不可用或网络延迟高，可能影响锁的可靠性。

```go
var ctx = context.Background()

func main() {
    // 连接到 Redis
    rdb := redis.NewClient(&redis.Options{
        Addr:     "localhost:6379", // Redis 地址
        Password: "",              // 密码 (无密码则留空)
        DB:       0,               // 使用默认 DB
    })

    lockKey := "my_lock"
    lockValue := "my_random_value" // 实际应用中，可以使用更复杂的随机值

    // 尝试获取锁
    lockAcquired, err := rdb.SetNX(ctx, lockKey, lockValue, 10*time.Second).Result()
    if err != nil {
        panic(err)
    }

    if lockAcquired {
        fmt.Println("Lock acquired, doing some work...")
        // 执行同步的操作
        time.Sleep(5 * time.Second) // 假设的工作负载

        // 释放锁
        _, err = rdb.Del(ctx, lockKey).Result()
        if err != nil {
            panic(err)
        }
        fmt.Println("Lock released")
    } else {
        fmt.Println("Could not acquire lock")
    }
}
```

#### 缓存淘汰策略，过期删除策略

在 Redis 这样的缓存系统中，缓存淘汰策略是用来决定当内存使用达到限制时哪些数据应该被移除的机制。缓存淘汰对于维护缓存系统的性能和高效利用有限的内存资源至关重要。

**常见的缓存淘汰策略**

- **无淘汰（noeviction）**：

  - 当内存达到限制时，所有导致内存增长的命令都会报错。

  - 适用于内存不受限制的情况。

- **全部随机（allkeys-random）**：

  - 随机移除任何键。

  - 没有特别的优先级或模式，完全随机。

- **最近最少使用（LRU, least recently used）**：

  - 移除最近最少使用的键。

  - Redis 实现了两种近似的 LRU 算法：volatile-lru 和 allkeys-lru。

  - volatile-lru 仅适用于设置了过期时间的键，而 allkeys-lru 对所有键有效。

- **最少访问（LFU, least frequently used）**：

  - 移除最少访问的键。

  - 类似于 LRU，但是基于访问频率而非时间。

  - Redis 提供 volatile-lfu 和 allkeys-lfu 两种选项。

- **最近最少使用（TTL, time to live）**：

  - 移除即将过期的键。

  - Redis 的 volatile-ttl 策略会选择最近将过期的键进行淘汰。

- **随机移除（volatile-random）**：

  - 随机移除已设置过期时间的键。

  - 仅适用于设置了过期时间的键。

**过期删除策略**

除了缓存淘汰策略，Redis 还实现了对键的过期删除策略：

- **被动删除**：当访问一个已经过期的键时，Redis 会删除它。
- **主动删除**：Redis 定期随机测试一些键，删除其中已经过期的键。这是一个折中方案，旨在平衡内存使用和性能。

**选择合适的策略**

选择哪种淘汰策略取决于具体的应用场景和需求：

- 如果不希望删除任何数据，可以选择 noeviction 策略。
- 对于缓存系统，通常会选择基于 LRU 或 LFU 的策略。
- 如果内存限制非常严格，可能需要更积极的淘汰策略，如 allkeys-lru 或 allkeys-lfu（ Redis 配置文件中设置 ）。

#### 日志

##### 1、日志类型：rdb/aof

这两种日志类型用于持久化，即将内存中的数据保存到磁盘上，以防止数据因进程崩溃或系统故障而丢失。

- **RDB（Redis Database）**

  RDB 是一种进行点时间快照的持久化方法。它会在特定的间隔捕捉存储在 Redis 中的数据并将其保存到磁盘上的一个文件中。

  - **生成快照**：可以根据配置（例如，每隔一定时间或达到一定更新数量）自动触发，也可以手动触发（使用 SAVE 或 BGSAVE 命令）。

  - **恢复数据**：当 Redis 重新启动时，它可以从 RDB 文件快速恢复数据。

  - **优点**：RDB 文件通常更小，且在灾难恢复时可以更快地加载。

  - **缺点**：RDB 可能会丢失最近的数据（自上次快照以来的数据），因为它不是实时记录数据变化的。

- **AOF（Append Only File）**

  AOF 采用日志追加方式记录每一个写操作命令，这些命令会被追加到 AOF 文件的末尾。

  - **实时记录**：每个修改数据的命令都会被追加到 AOF 文件中。

  - **数据恢复**：重启时，Redis 通过重放 AOF 文件中的命令来恢复原始数据。

  - **文件重写**：随着操作的积累，AOF 文件可能会变得很大。Redis 提供 AOF 重写机制来压缩 AOF 文件，只保留恢复当前数据状态所必需的命令。

  - **优点**：提供了更好的持久化保障，因为它几乎不会丢失任何数据。

  - **缺点**：AOF 文件可能会比 RDB 文件大，且重放 AOF 文件的恢复速度可能比加载 RDB 文件慢。

**使用建议**

- **选择合适的持久化策略**：根据您的需要（是否需要最小化数据丢失、恢复速度要求等）来选择使用 RDB、AOF，或者两者结合。
- **RDB 和 AOF 结合使用**：在很多情况下，同时使用 RDB 和 AOF 可以提供既快速的恢复速度（通过 RDB），又有很好的数据完整性保障（通过 AOF）。
- **定期备份**：无论使用哪种持久化方法，定期备份都是非常重要的，以防止数据丢失。

##### 2、写回策略，生成时机，刷盘时机

在 Redis 和许多其他数据库或缓存系统中，写回策略、快照的生成时机和刷盘时机是重要的概念，它们影响着数据的持久性、系统性能和数据一致性。

- **写回策略**

  写回策略决定了数据何时从内存写入到磁盘。在 Redis 中，这通常关联到 RDB 和 AOF 持久化机制：

  - **RDB (Redis Database)**：

    - 定期生成整个数据集的快照。

    - 可以配置生成快照的频率（例如，每隔一定分钟数或达到一定的写操作数量）。

  - **AOF (Append Only File)**：

    - 记录每个写操作并追加到 AOF 文件中。

    - 可以配置为每次写操作后刷盘（同步）、每秒刷盘（异步，每秒一次）或由操作系统决定何时刷盘。

- **快照的生成时机**

  - **定时快照**：可以在 Redis 配置中指定特定的间隔（基于时间或写操作的数量）来自动触发 RDB 快照的创建。

  - **手动触发**：使用 SAVE 或 BGSAVE 命令可以随时手动创建快照。

- **刷盘时机**

  - **同步刷盘**：在 AOF 持久化中，如果配置为每次写操作后刷盘，系统会在每个写命令执行后立即将数据写入磁盘。这种方式提供了最高的数据安全性，但可能会影响性能。

  - **异步刷盘**：更常见的配置是每秒刷盘，它提供了良好的平衡，确保数据在一秒内被写入磁盘，同时减少了对性能的影响。

  - **操作系统刷盘**：这种方式下，刷盘操作由操作系统在合适的时机进行，通常依据内存缓冲区的状态。

#### 常见问题

##### 1、缓存击穿/穿透/雪崩，大key/热key，常见阻塞原因

- **缓存击穿**

  - **定义**：缓存击穿指的是高并发访问某个热点 Key 时，该 Key 刚好失效，导致所有请求都去查询数据库。

  - **解决方案**：为热点 Key 设置永不过期，或者使用互斥锁，确保同一时间只有一个请求去数据库查询并更新缓存。

- **缓存穿透**

  - **定义**：缓存穿透是指查询不存在的数据，由于缓存不命中，导致每次都要去数据库查询。

  - **解决方案**：将查询结果为空的响应也缓存起来，或使用布隆过滤器拦截掉不存在的查询请求。

- **缓存雪崩**

  - **定义**：缓存雪崩是指缓存中的大量数据在同一时间失效，导致大量请求落到数据库上，可能引起数据库瘫痪。

  - **解决方案**：设置不同的过期时间，避免同时大量 Key 失效；使用高可用的缓存解决方案，如 Redis 集群，雪崩出现故障时使用另一个。

- **大 Key 问题**

  - **定义**：单个 Key 存储的数据量过大，比如一个超大的 List、Hash。

  - **问题**：操作大 Key 可能会阻塞 Redis，影响性能。

  - **解决方案**：避免存储大 Key，将大 Key 拆分成多个小 Key。

- **热 Key 问题**
  - **定义**：某些 Key 非常热门，被大量并发访问。
  - **问题**：可能导致缓存服务的负载不均衡。
  - **解决方案**：对热 Key 实施负载均衡，如通过增加副本来分散读取压力。

**常见阻塞原因**

- **长时间运行的命令**：如对大 Key 进行操作（例如大范围的 HGETALL，获取存储在指定哈希（Hash）键中的所有字段（fields）和值（values））。
- **资源耗尽**：比如 Redis 内存耗尽。
- **网络问题**：缓慢的网络或大量的网络请求导致的瓶颈。
- **客户端问题**：过多的客户端连接或客户端长时间不释放连接。

#### 线程模型

##### 1、IO多路复用，文件时间分派器，事件处理器

Redis 的线程模型主要基于 I/O 多路复用、文件事件分派器和事件处理器这几个核心组件。这个模型是 Redis 高性能和高吞吐量的关键。

- **I/O 多路复用**

  I/O 多路复用是一种允许单个线程监视和管理多个 I/O 流（如网络连接）的技术。它可以有效地处理多个并发客户端连接，而不需要为每个连接创建和管理单独的线程或进程。这减少了上下文切换的开销，提高了效率。

  - 在 Redis 中，I/O 多路复用用于同时处理来自客户端的所有输入/输出请求。

  - Redis 支持多种 I/O 多路复用库，如 select, epoll, kqueue 等，具体使用哪个取决于操作系统。

- **文件事件分派器**

  文件事件分派器是 Redis 事件循环的一部分，负责接收并分派来自多个客户端的事件。这些事件可能包括新的连接请求、收到的命令或需要写回客户端的响应。

  - 当 I/O 多路复用器通知 Redis 一个或多个套接字（socket）已准备好进行读取或写入时，文件事件分派器就会触发相应的事件处理器。

- **事件处理器**

  每当文件事件分派器接收到事件时，相应的事件处理器就会被触发。这些处理器负责实际处理事件，如读取客户端命令、执行命令和发送回响应。

  - 事件处理器使得 Redis 能够高效地处理不同类型的事件，包括网络请求和定时任务。

- **Redis 线程模型的特点**

  - **单线程处理命令**：虽然 Redis 使用单线程来处理命令，但由于其高效的事件处理机制和数据存储在内存中，Redis 能够提供极高的性能。

  - **多线程 I/O**：在 Redis 6.0 以后的版本中，引入了多线程来处理网络 I/O（接收网络请求和向网络发送响应），但数据的读取和写入（对内存或磁盘中数据的操作）仍然是单线程的。

- **套接字（socket）**

套接字（socket）是计算机网络中的一个抽象概念，用于在不同主机之间或同一主机内的不同进程之间进行数据交换。套接字是网络通信的基石，提供了一个统一的编程接口，以便不同的网络协议（如 TCP、UDP）和不同的操作系统之间能够进行通信。

- **select、poll、epoll、kqueue**

  - **select**

    - **工作原理**：select 允许程序监控多个文件描述符，等待一个或多个文件描述符成为“就绪”状态，即它们有数据可读取、可写入，或出现异常。

    - **限制**：

      - 文件描述符数量限制：select 受限于它可以监控的文件描述符数量上限（通常由系统定义）。

      - 性能问题：它在每次调用时都需要重新传入所有被监控的文件描述符，且内核需要遍历整个文件描述符集合，因此在处理大量文件描述符时效率不高。

  - **epoll**

    - **特点**：epoll 是 Linux 特有的 I/O 多路复用机制，它解决了 select 的一些限制。

    - **工作原理**：epoll 使用一种事件通知机制，只处理那些“就绪”的文件描述符。它在内核中维护一个事件表，这使得无需重复传递监听列表，提高了效率。

    - **优点**：
      - 可以处理更多的文件描述符。
      - 提高了处理大量文件描述符的性能。

  - **kqueue**

    - **特点**：kqueue 是 FreeBSD、macOS 等 BSD 系统特有的 I/O 多路复用解决方案。

    - **工作原理**：与 epoll 类似，kqueue 也是基于事件驱动的，能够高效地管理大量文件描述符。

    - **应用**：它支持更广泛的事件类型，不仅仅限于网络 I/O，还包括文件系统事件、信号处理等。

  - **poll**

    - **概述**：poll 是一个标准的 UNIX 系统调用，提供了一种方法来监视多个文件描述符的 I/O 准备就绪状态。

    - **工作原理**：poll 使用一个 pollfd 结构的数组，每个结构包含一个文件描述符和一组感兴趣的事件以及发生的事件。

    - **特点**：

      - poll 没有文件描述符数量的固定限制（与 select 相比）。

      - 适用于各种类型的 Unix 系统，包括 Linux 和 BSD。

#### 主从复制同步，哨兵模式，集群模式

- **主从复制同步（Replication）**

  主从复制是 Redis 最基本的高可用性和数据冗余方案。

  - **工作原理**：
    - 在这种模式下，数据从一个 Redis 服务器（主节点）自动复制到一个或多个 Redis 服务器（从节点）。
    - 从节点可以用于读取操作，以此来分摊主节点的读取负载。

  - **数据同步**：
    - 当主节点的数据发生变化时（如更新、删除操作），这些变化会被同步到所有从节点。
    - 从节点启动时，会从主节点进行全量同步。

  - **故障转移**：
    - 如果主节点发生故障，需要手动将其中一个从节点提升为新的主节点，并重新配置其他从节点以指向新的主节点。

- **哨兵模式（Sentinel）**

  哨兵模式在主从复制的基础上增加了自动故障转移的功能。

  - **工作原理**：
    - 哨兵是一个独立的进程，它监控主节点和从节点的健康状况。
    - 它可以自动执行故障转移，比如在主节点不可用时自动将一个从节点升级为新的主节点。

  - **自动故障转移**：
    - 哨兵之间会相互通信，以决定何时一个主节点被认为是不可用的，并启动故障转移过程。

  - **配置和监控**：
    - 哨兵模式不仅提供故障转移，还可以用于系统报警和自动发现新的 Redis 实例。

- **集群模式（Cluster）**

  Redis 集群是一个为了获得更高性能和可扩展性而设计的分布式数据库解决方案。

  - **工作原理**：
    - 在集群模式下，数据被自动分片到多个 Redis 节点上。
    - 每个节点只保存数据的一部分，客户端请求会被自动重定向到正确的节点。

  - **高可用性和数据分片**：
    - 集群中的每个节点都有一到多个复制节点，可以在主节点故障时自动接管。
    - 数据分片（分区）使得集群可以处理比单个 Redis 实例更大的数据集和更高的吞吐量。

  - **无中心结构**：
    - Redis 集群没有中心节点，每个节点都存储数据并处理请求，节点之间通过 Gossip 协议进行通信。

- **总结**

  - **主从复制**适用于数据备份和读负载分摊。

  - **哨兵模式**在主从复制的基础上增加了自动故障转移，适用于要求高可用性的场景。

  - **集群模式**适用于大规模数据存储和高吞吐量的场景，提供数据自动分片和更强的故障容错能力。

### hbase

Apache HBase是一个开源的、分布式的、版本化的非关系型数据库，它基于Google的Bigtable模型构建。HBase允许进行大规模的数据存储，同时提供快速的随机访问能力。它通常用于存储大量的稀疏数据集，如大表。

- **HBase的基本概念**

  - **表（Table）**:类似于关系型数据库中的表，用于存储数据。

  - **行（Row）**:表中的每条记录，由唯一的行键（Row Key）标识。

  - **列族（Column Family）**:数据的容器，每个表可以有一个或多个列族。所有列族都必须在创建表时定义。

  - **列（Column）**:列是列族中的一个元素。在HBase中，列由列族和列标识符组合而成。

  - **时间戳（Timestamp）**:HBase中的每个数据版本都有相应的时间戳。

#### 了解table/row/column family/column qualifier/cell概念

- **Table（表）**

  - **定义:**HBase中的表是数据存储的顶层单位，类似于关系型数据库中的表。

  - **特点:**表由行（Rows）组成，并按行键（Row Key）排序存储。

- **Row（行）**

  - **定义**:表中的每一行代表一个记录，由一个唯一的行键（Row Key）标识。

  - **特点**:行键是字节串，HBase根据行键的字典顺序存储数据，优化了基于行键的查询。

- **Column Family（列族）**

  - **定义**: 列族是表中的一个主要组成部分，每个表可以有一个或多个列族。

  - **特点**: 列族内包含实际的数据列（Column Qualifier），所有列族成员必须在表创建时定义。列族存储在文件系统中，通常每个列族都存储在单独的文件中。

- **Column Qualifier（列限定符）**

  - **定义**:列限定符是列族中的子列，可以看作是表中的一个字段。

  - **特点**:在HBase中，列由列族和列限定符共同标识，通常表示为 **column_family:qualifier**。列限定符是动态的，不需要在表创建时定义。

- **Cell（单元格）**

  - **定义**:单元格是HBase表中的最小数据单位，由行键、列族、列限定符和时间戳唯一确定。

  - **特点**:单元格内存储着实际的值。每个单元格可以有多个版本，每个版本通过时间戳区分。

- **实例说明**

  - **Table**: Students

  - **Row Key**: 学生ID

  - **Column Family**: PersonalDetails, AcademicRecords

  - **Column Qualifier**: `PersonalDetails:Name, AcademicRecords:Grade

  - **Cell**: 每个单元格存储特定学生的特定信息（如“Alice的成绩”）。

在这个例子中，Students 表用于存储学生的个人详细信息和学术记录。每个学生的记录是一行，用学生ID作为行键。个人详细信息（如姓名）存储在 PersonalDetails 列族中，而学术记录（如成绩）存储在 AcademicRecords 列族中。每个信息（如姓名或成绩）是列族中的一个列限定符。单元格中存储的是具体的数据，如Alice的姓名或成绩。

#### 结构

##### 1、数据模型，列式存储

- **概述**:
  - HBase是一个列式数据库，这意味着它是按列（而非按行）组织和优化数据的。这种结构特别适合于大数据的存储和访问。
- **特点**:
  - **列族**: 数据按列族（Column Family）存储，每个列族下可以有多个列限定符（Column Qualifier）。在物理上，同一列族的数据存储在一起。
  - **稀疏性**: HBase表是稀疏的，意味着它只存储非空数据。这减少了存储空间的需求，并优化了查询性能。

##### 2、索引结构，LSM Tree

- **概述**:
  - HBase使用LSM树（Log-Structured Merge-Tree）作为其底层的索引和存储结构。
- **特点**:
  - **写优化**: LSM树是为了高效的写操作而设计的，它首先将写操作存储在内存中的结构（如MemStore），然后定期异步刷写到磁盘。
  - **合并和压缩**: 定期地在后台进行数据文件的合并和压缩操作，优化读操作性能。
  - **Bloom Filter**: 用于快速检查一个键是否存在于某个SSTable（Sorted String Table）中，减少磁盘I/O。

##### 3、存储结构，key-value各字段内容

- **概述**:
  - HBase的数据存储为键值对（Key-Value）格式。每个键值对包含行键（Row Key）、列族、列限定符和时间戳组成的复合键。
- **特点**:
  - **复合键**: 键是由行键、列族、列限定符和时间戳组合而成，确保了每个单元格的唯一性。
  - **版本控制**: 通过时间戳实现版本控制，每个单元格可以存储多个版本的数据。
  - **行键设计**: 行键的设计对于查询性能至关重要，应尽可能地避免热点问题。

#### 行键，列组设计方案

- **行键（Row Key）设计**

  - **唯一性**:行键必须是唯一的，因为它用于唯一标识表中的每一行。

  - **均衡分布**:行键的设计应该避免热点问题。选择或设计行键时，确保数据在RegionServer之间均匀分布。

  - **有意义的顺序**:如果业务场景中存在范围扫描的需求，设计行键时可以考虑其顺序性。

  - **长度和大小**:行键应该尽量短，以减少存储空间的消耗和内存使用，同时提高处理速度。

  - **避免频繁变更**:行键一旦设定，在HBase中不能修改。如果需要更新行键，必须插入一个新行并删除旧行。

- **列族（Column Family）设计**

  - **数据访问模式**:将经常一起访问的数据放在同一个列族中。HBase在物理上是按列族存储数据的，所以这可以优化读取性能。

  - **数量限制**:列族的数量不宜过多。每增加一个列族，都会增加存储和管理的开销。

  - **大小考虑**:注意列族中数据的大小，避免单个列族过大，导致读写性能下降。

  - **版本和TTL**:根据需要设定列族中数据的版本（version）和生存时间（TTL）。适当的版本控制可以方便数据回溯，而TTL则可以帮助自动清理过期数据。

**行键设计实例**

- **行键**: 可以将用户ID和时间戳组合作为行键，例如 userID_timestamp 。这样设计行键既保证了唯一性，又因为用户ID均匀分布，可以避免热点问题。
- **列族**: 根据数据的访问模式，可以将用户的基本信息放在一个列族中，将用户的行为日志放在另一个列族中。

### mongo

#### 了解database/collection/document/filed/index概念

- **Database（数据库）**

  - **定义**:在MongoDB中，数据库是一组集合（collections）的容器。每个数据库都是独立的，拥有自己的设置和权限。

  - **用途**:通常根据应用或数据的逻辑分组来创建不同的数据库。

- **Collection（集合）**

  - **定义**:集合是MongoDB文档的组，类似于关系型数据库中的表。它不强制其内容遵循相同的结构。

  - **特点**:在MongoDB中，集合可以存储不同结构的文档，提供了很大的灵活性。

- **Document（文档）**

  - **定义**:文档是MongoDB数据的基本单元，由键值对构成。MongoDB文档类似于JSON对象，但其实使用的是BSON（一种类似于JSON的二进制格式）。

  - **特点**:文档可以包含不同的数据类型和嵌套的文档。

- **Field（字段）**

  - **定义**:字段是文档中的一个键值对。每个文档都由一个或多个字段组成。

  - **特点**:字段的值可以是各种数据类型，包括另一个文档、数组或文档数组。

- **Index（索引）**

  - **定义**:索引是对数据库集合中一个或多个字段的值进行排序的数据结构，可以提高数据检索的速度。

  - **特点**:索引类似于书籍的目录，可以大大加快查询的速度。MongoDB支持多种类型的索引，如单字段索引、复合索引、文本索引等。

**总结**

- **Database**: 数据库是数据的集合，每个数据库包含多个集合。
- **Collection**: 集合类似于表，是文档的组。
- **Document**: 文档是数据记录，以BSON格式存储。
- **Field**: 字段是文档中的一个键值对。
- **Index**: 索引用于优化数据的检索速度。

#### 数据模型

在MongoDB中，数据以灵活的文档结构存储，这些文档是BSON（一种类似JSON的二进制格式）格式。

##### 1、文档结构，文件/字段限制

- **文档结构**

  - 文档是MongoDB中的基本数据单位，类似于JSON对象，由字段和值对组成。

  - 字段（Field）可以包含各种数据类型的值，包括其他文档、数组和文档数组。

- **文件和字段限制**

  - **文档大小限制**: MongoDB限制单个文档的最大大小为16MB。这是为了确保单个文档能够在网络中高效传输，并在内存中有效处理。

  - **字段命名限制**: 字段名不能包含 \0（空字符，表示字符串的结尾），不能以 $ 字符开始，也不能包含 . 字符。

##### 2、嵌套文档，子集模式，引用方式

- **嵌套文档（子文档）**

  - 嵌套文档允许您在单个文档中存储复杂的层级数据。

  - 这些嵌套文档可以是任意深度，但仍需遵守16MB的文档大小限制。

  - 嵌套文档通常用于存储相关数据，这些数据通常一起使用。

- **子集模式**

  - 子集模式（Subdocuments）是指在一个文档中嵌套另一个文档。

  - 这对于描述具有多个层级的数据结构非常有用，例如，地址信息可以作为用户文档的子集嵌入。

- **引用方式**

  - MongoDB支持两种主要的引用方式：嵌入式引用和规范化引用。

  - **嵌入式引用**: 将相关数据直接嵌入文档中。这种方式使读取操作更快，因为所有相关数据都存储在单个文档中。

  - **规范化引用**: 使用文档的ID来引用其他文档。这种方式类似于关系型数据库中的外键，并允许数据存储在多个文档中。

  - 选择嵌入式引用或规范化引用取决于应用的特定需求，如数据访问模式、更新频率和数据一致性要求。

#### 存储

##### 1、存储引擎

- **概述**:存储引擎是MongoDB的一个组件，负责管理数据的存储方式，包括数据的组织、存储格式、索引和文件管理等。

- **主要类型**

  - **WiredTiger**: 从MongoDB 3.0版本开始，默认的存储引擎。它提供了文档级别的锁定和压缩，支持更高的并发和更好的性能。

  - **MMAPv1**: MongoDB的早期存储引擎，提供了集合级别的锁定。在新版本中已被WiredTiger替代。

  - **In-Memory**: 一个商业存储引擎，提供了在内存中完全存储数据的能力，用于需要极高读写速度的场景。

##### 2、分片管理

- **概述**:分片是MongoDB中处理大数据集和高吞吐量操作的一种方法。通过分片，数据被分散存储在多个服务器上。

- **如何工作**

  - **Shard**: 存储数据的物理节点，每个分片包含数据的一个子集。

  - **Mongos**: 查询路由器，接受客户端的请求，并将其路由到正确的分片。

  - **Config Servers**: 存储集群的元数据，如分片的信息和数据分布情况。

- **分片策略**

  - **范围分片（Range Sharding）**: 根据字段的范围将数据分布到不同的分片。

  - **哈希分片（Hash Sharding）**: 根据字段的哈希值分配数据，提供了更均匀的数据分布。

##### 3、副本集

- **概述**:副本集是MongoDB中的一组服务器，它们存储相同的数据集。副本集提供了数据的冗余备份和高可用性。

- **主要特点**

  - **自动故障转移**: 如果主节点（Primary）发生故障，副本集可以自动选举一个新的主节点。

  - **数据冗余**: 所有数据在多个节点上有副本，提高了数据安全性。

  - **读写分离**: 可以从副本节点（Secondary）读取数据，以分担主节点的读取压力。

#### 索引

##### 1、索引类型

###### 单值，复合，多建，哈希等

- **单字段索引（Single Field）**
  - 在单个字段上创建索引。除了 _id 字段上的默认索引外，您可以在任何字段上创建单字段索引。

- **复合索引（Compound Index）**
  - 在多个字段上创建索引，以支持多个字段的查询。复合索引中字段的顺序很重要，因为它决定了索引的效率。

- **多键索引（Multikey Index）**
  - 用于索引数组类型的字段。如果索引的字段是数组类型，MongoDB会创建多键索引，使数组中的每个元素都被索引。

- **哈希索引（Hashed Index）**
  - 基于哈希值的索引，适用于均匀分布数据的场景。它们常用于分片配置中。

- **地理空间索引（Geospatial Index）**
  - 用于地理空间数据的查询。例如，可以用于查询特定距离内的地理位置。

- **文本索引（Text Index）**
  - 用于在文档的字符串字段上执行全文搜索。

##### 2、索引设计策略

- **索引选择和查询模式**
  - 根据应用的查询模式选择索引。理解应用中最常用的查询类型，并基于这些查询类型创建索引。

- **考虑索引顺序**
  - 在创建复合索引时，考虑查询中字段的顺序。字段在复合索引中的顺序会影响查询的效率。

- **避免过多索引**
  - 过多的索引会增加写操作的负担，因为每次数据变更都需要更新所有的索引。同时，每个索引都会占用额外的存储空间。

- **监控和评估**
  - 使用MongoDB的性能监控工具，如`explain()`方法，来评估查询的执行计划和索引的效率。

- **索引维护**
  - 定期评估索引的效果。随着数据模式的变化和应用的发展，某些索引可能变得不再有效。

#### 事务操作

#### 开始一个事务

在MongoDB中，事务是在会话（session）的上下文中开始的。首先，您需要启动一个新的会话，然后在该会话中启动事务。

**示例**

```go
func main() {
    // 连接到MongoDB
    client, err := mongo.Connect(context.TODO(), options.Client().ApplyURI("mongodb://localhost:27017"))
    if err != nil {
        panic(err)
    }
    defer client.Disconnect(context.TODO())

    // 开始一个会话
    session, err := client.StartSession()
    if err != nil {
        panic(err)
    }
    defer session.EndSession(context.Background())

    // 开始一个事务
    err = session.StartTransaction()
    if err != nil {
        panic(err)
    }

    // 执行事务操作
    err = mongo.WithSession(context.Background(), session, func(sc mongo.SessionContext) error {
        // 这里数据库操作
        

        // 如果一切正常，则提交事务
        if err := session.CommitTransaction(sc); err != nil {
            return err
        }
        return nil
    })

    if err != nil {
        panic(err)
    }
}
```

**注意事项**

- **持久性**:事务在MongoDB中保证了ACID属性（原子性、一致性、隔离性、持久性）。
- **性能考虑**:尽管事务提供了强大的一致性保证，但它们可能会影响性能，尤其是在高负载的系统中。
- **重试逻辑**:应该实现适当的重试逻辑来处理可能的事务冲突，特别是在高并发环境下。
- **版本要求**:使用事务需要MongoDB的副本集，且版本至少为4.0。在分片集群中，MongoDB 4.2及以上版本支持事务。
- **操作限制**:在事务中，某些操作可能受到限制。建议查阅MongoDB的官方文档，以了解最新的操作限制。

### elasticsearch

Elasticsearch是一个基于Lucene构建的开源全文搜索和分析引擎，它以其高速、可扩展和简单的RESTful API而广受欢迎。

#### 核心概念

##### 1、索引 index

- **定义**:在Elasticsearch中，索引是具有某些相似特征的文档集合。每个索引都有一个名称，该名称必须是小写的。
- **用途**:类似于传统数据库中的“数据库”，是数据存储和搜索的基础。

##### 2、类型 type【已弃用】

- **定义**:类型是索引内的逻辑分类/分区，用于将不同种类的文档组织在一起。
- **弃用说明**:在Elasticsearch 6.x中，类型的概念被弃用，并在7.x版本中完全移除。现在建议每个索引只对应一种类型的数据。

##### 3、文档 document

- **定义**:文档是可以被索引的基本信息单位。每个文档都用JSON格式表示，并具有一个唯一的ID。
- **用途**:类似于关系型数据库中的“行”，是存储实际数据的地方。

##### 4、字段 filed

- **定义**:字段是文档的基本单位，每个字段都有一个名称和数据类型。
- **用途**:类似于数据库中的“列”，字段存储数据值和数据类型。

##### 5、映射 mapping 

- **定义**:映射类似于数据库中的“表结构定义”，它定义了文档及其包含的字段如何被存储和索引。
- **用途**:指定字段的数据类型（如整数、字符串、日期）、是否被索引、是否存储原始数据等。

#### 索引管理

索引管理主要涉及创建索引、更新映射、优化索引性能和删除索引等操作。

- **创建索引**

  ```json
  PUT /my_index
  {
    "settings": {
      "number_of_shards": 3,
      "number_of_replicas": 2
    }
  }
  ```

- **更新映射**

  映射是定义文档及其字段如何存储和索引的规则。一旦创建了索引，你就不能更改现有字段的映射。如果需要，你可以向索引添加新的字段。

  ```json
  PUT /my_index/_mapping
  {
    "properties": {
      "new_field": {
        "type": "text"
      }
    }
  }
  ```

- **优化和维护索引**

  定期优化和维护索引对于保持Elasticsearch集群的健康和性能至关重要。

  - 使用 _forcemerge API减少索引片段。

  - 清理未使用的索引以节省空间。

  - 监控索引性能和健康状况。

- **删除索引**

  当索引不再需要时，可以将其删除。

  ```json
  DELETE /my_index
  ```

#### 复合查询

##### 1、布尔查询

布尔查询允许你结合多个子查询，如must（必须）、should（应该）、must_not（不必须）和 filter（过滤）。

**示例**

```json
GET /_search
{
  "query": {
    "bool": {
      "must": [
        { "match": { "title": "search" }}
      ],
      "filter": [
        { "term": { "status": "published" }}
      ],
      "must_not": [
        { "range": { "age": { "gte": 30 }}}
      ],
      "should": [
        { "term": { "tag": "tech" }}
      ]
    }
  }
}
```

##### 2、提高查询

提升查询用于降低不符合某个条件的文档的相关性评分。

**示例**

```json
GET /_search
{
  "query": {
    "boosting": {
      "positive": {
        "term": { "text": "apple" }
      },
      "negative": {
        "term": { "text": "mac" }
      },
      "negative_boost": 0.2
    }
  }
}
```

##### 3、固定分数

固定分数查询为符合过滤器条件的所有文档返回一个固定的分数。

**示例**

```json
GET /_search
{
  "query": {
    "constant_score": {
      "filter": {
        "term": { "category": "news" }
      },
      "boost": 1.2
    }
  }
}
```

##### 4、最佳匹配

最佳匹配查询用于当有多个字段，但希望匹配至少一个字段时使用。

**示例**

```json
GET /_search
{
  "query": {
    "dis_max": {
      "queries": [
        { "term": { "title": "war" }},
        { "term": { "content": "war" }}
      ],
      "tie_breaker": 0.7
    }
  }
}
```

##### 5、函数查询

函数查询用于修改查询的相关性评分，可以根据不同的函数来调整分数。

**示例**

```json
GET /_search
{
  "query": {
    "function_score": {
      "query": { "match": { "message": "elasticsearch" }},
      "boost": "5",
      "functions": [
        {
          "filter": { "match": { "title": "search" }},
          "weight": 23
        },
        {
          "random_score": {}, 
          "weight": 42
        }
      ],
      "max_boost": 42,
      "score_mode": "max",
      "boost_mode": "multiply",
      "min_score": 42
    }
  }
}
```

#### 聚合查询

聚合查询是用来进行数据分析和汇总的强大工具。

##### 1、bucket聚合

桶聚合主要用于对文档集进行分组，每个桶都对应一个键值和文档的集合。

**示例：条款聚合（Terms Aggregation）**

用于创建基于某个字段的不同值的文档组。

```json
GET /_search
{
  "aggs": {
    "group_by_state": {
      "terms": {
        "field": "state"
      }
    }
  }
}
```

这个例子中，我们对“state”字段的不同值进行分组，每个组（桶）包含拥有相同“state”值的所有文档。

##### 2、metrics聚合

度量聚合用于对文档集或文档集中的字段进行计算统计。

**示例：平均聚合（Average Aggregation）**

用于计算指定字段的平均值。

```json
GET /_search
{
  "aggs": {
    "average_age": {
      "avg": {
        "field": "age"
      }
    }
  }
}
```

在这个例子中，我们计算所有文档中“age”字段的平均值。

##### 3、pipeline聚合

管道聚合允许你基于其他聚合的结果进行聚合操作。

**示例：累计和聚合（Cumulative Sum Aggregation）**

用于计算之前聚合的累计和。

```json
GET /_search
{
  "aggs": {
    "sales_per_month": {
      "date_histogram": {
        "field": "date",
        "calendar_interval": "month"
      },
      "aggs": {
        "sales": {
          "sum": {
            "field": "sales"
          }
        },
        "cumulative_sales": {
          "cumulative_sum": {
            "buckets_path": "sales"
          }
        }
      }
    }
  }
}
```

这个例子中，首先我们按月对销售数据进行分组（“sales_per_month”），然后计算每个月的销售总额（“sales”），最后使用累计和聚合（“cumulative_sales”）来累加之前每个月的销售额。

#### 文档存储，分片

Elasticsearch的文档存储和分片机制是理解其数据组织和检索能力的关键组成部分。这些机制确保了Elasticsearch在处理大规模数据集时的高效性和可扩展性。

- **文档存储**

  在Elasticsearch中，数据以文档的形式存储。这些文档是JSON对象，包含了各种字段和对应的值，类似于NoSQL数据库中的记录。

  - **特点**

    - **基于JSON**:文档是以JSON格式存储，使得数据结构灵活、自描述且易于理解。

    - **无模式（Schema-less）**:Elasticsearch可以接受任何结构的JSON文档，不需要预先定义模式。不过，定义映射（Mapping）可以更好地控制数据如何被索引和存储。

    - **全文搜索能力**:文档的存储方式优化了全文搜索和复杂查询的性能。

    - **反向索引**:为了实现快速的搜索，Elasticsearch在背后为文档字段创建反向索引。

- **分片（Sharding）**

  Elasticsearch使用分片来水平分割数据。每个索引都可以被分割成多个分片，每个分片是索引的一个子集。

  - **为什么使用分片**

    - **水平扩展**:分片允许Elasticsearch分布式地存储大量数据，使得数据集可以跨多个服务器存储。

    - **性能提升**:分布式处理和存储可以提高读写能力和速度。

  - **分片类型**

    - **主分片（Primary Shard）**:每个文档都存储在一个主分片上。主分片的数量在创建索引时定义，之后不能更改。

    - **副本分片（Replica Shard）**:主分片的副本，用于提供数据冗余和增强搜索性能。副本分片的数量可以随时更改。

  - **分片的选择和分配**

    - 分片的数量和分布对性能和可扩展性有重要影响。

    - 主分片的数量决定了索引能够存储的最大数据量，而副本分片数影响数据的可用性和搜索性能。

    - Elasticsearch自动管理分片的位置和负载均衡。

**注意事项**

- 选择合适的分片数量对于性能优化至关重要。过多的分片可能会导致资源浪费，而过少的分片可能限制了可扩展性。
- 在文档设计时，应考虑到数据的检索方式和分析需求，以优化存储和搜索性能。
- 在分布式环境中，合理配置和监控分片对于维护系统的稳定性和效率非常重要。

#### 批量操作

在Elasticsearch中，批量操作（bulk API）是一种高效处理多个索引、更新或删除操作的方法。使用bulk API，可以在单个请求中发送多个操作，从而显著减少网络开销并提高性能。这在处理大量数据时尤为重要，例如在数据迁移或批量导入数据时。

##### 1、bulk

- **使用Bulk API进行批量操作**

  - **基本语法**

    bulk API允许您在一个请求中组合多个index、create、update或delete操作。每个操作由两行组成：第一行描述操作类型和目标（_index、_type、_id），第二行是操作的源文档或数据（对于index、create和update）。

  - **示例**

    以下是一个使用bulk API的示例，它包含了索引（添加）和删除操作：

    ```json
    POST /_bulk
    { "index": { "_index": "my_index", "_id": "1" }}
    { "field1": "value1", "field2": "value2" }
    { "delete": { "_index": "my_index", "_id": "2" }}
    { "index": { "_index": "my_index", "_id": "3" }}
    { "field1": "value3", "field2": "value4" }
    ```

    这个例子中，我们向索引my_index添加两个文档（ID为1和3），并删除一个文档（ID为2）。

**注意事项**

- **性能优化**:
  - 批量操作可以显著提高大量数据处理的效率。但是，过大的批量请求可能会对Elasticsearch集群的性能产生负面影响。需要找到合适的批量大小以平衡性能和资源使用。
- **错误处理**:
  - bulk请求的响应包含每个操作的结果。成功的操作和失败的操作都会在响应中返回，因此需要正确处理可能出现的错误。
- **超时和限制**:
  - 根据Elasticsearch集群的配置和资源，bulk操作可能会受到超时和大小限制。在生产环境中，应根据实际情况调整请求大小和超时设置。
- **ID管理**:
  - 对于index 和 create 操作，如果没有指定文档ID，Elasticsearch会自动生成一个。如果需要保持文档的唯一性，建议显式指定文档ID。

## 消息队列

引入消息队列（Message Queue, MQ）在系统架构中提供了异步处理、服务解耦和流量削峰等多方面的优势。然而，使用消息队列也带来了一些潜在的缺点和挑战，包括可靠性问题、消息堆积和维护成本等。

### 引入消息队列的优缺点

#### 异步、解耦、削峰（优点）

- **异步处理（Asynchronous Processing）**

  - **减少等待时间**:应用可以将耗时的任务委托给消息队列处理，从而快速响应用户请求。

  - 提高系统响应性:通过异步处理，系统可以更有效地利用资源，增加吞吐量。

- **解耦（Decoupling）**

  - 降低依赖性:消息队列作为不同服务之间的中间层，减少了它们的直接依赖。

  - **灵活性和可维护性**:各组件之间的解耦使得系统更易于扩展和维护。

- **削峰（Peak Load Handling）**

  - **流量平衡**:在高流量情况下，消息队列可以帮助平衡负载，防止系统过载。

  - **提升用户体验**:即使在高负载情况下，用户也能获得较快的响应时间。

#### 可靠性问题，消息堆积，维护成本（缺点）

- **可靠性问题**

  - **消息丢失**:在网络问题或软件故障的情况下，可能会导致消息丢失。

  - **顺序问题**:在某些消息队列中，不能保证消息的严格顺序。

- **消息堆积**

  - **处理能力**:如果消息的生产速度超过消费速度，可能会导致消息在队列中堆积，增加延迟。

  - **资源限制**:大量的消息积压可能会消耗过多的存储和内存资源。

- **维护成本**

  - **复杂性**:引入消息队列增加了系统的复杂性，需要额外的维护和管理。

  - **监控需求**:需要实现对消息队列的监控，以确保其正常运行。

### 消息交付保障

在消息队列系统中，消息交付保障是确保消息正确传递的关键机制。

#### 至少一次 at least once

- **定义**:确保消息至少被交付一次。如果没有收到确认，消息可能会被重复发送。
- **应用场景**:适用于丢失消息代价高于处理重复消息的场景。
- **优点**:可以确保消息不会丢失。
- **缺点**:可能会导致消息重复，消费者需要处理重复消息的情况。

#### 至多一次 at most once

- **定义**:确保消息最多只被交付一次，可能会导致消息丢失，但不会重复发送。
- **应用场景**:适用于可以容忍消息丢失但不能处理重复消息的场景。
- **优点**:避免了消息重复。
- **缺点**:可能会导致消息丢失。

#### 精确一次 exactly once

- **定义**:确保每条消息只被精确地交付一次，既不会丢失也不会重复。
- **应用场景**:适用于需要高可靠性的场景，如金融交易处理。
- **优点**:提供了最高水平的可靠性保障。
- **缺点**:实现复杂，可能导致性能开销较大。

**实现考虑**

- **至少一次**和**至多一次**的保障相对容易实现，但它们分别需要处理重复消息和消息丢失的风险。
- **精确一次**交付是最理想的保障，但也是最难实现的。它通常需要复杂的协调机制和额外的性能开销。
- 在实际应用中，选择哪种交付保障取决于业务需求和系统容错能力。有时，结合使用应用层的逻辑来处理重复或丢失的消息可能是更实际的方法。

### kafka

#### 核心概念

Apache Kafka是一个分布式流处理平台，主要用于构建实时数据管道和流式应用。它以其高吞吐量、可扩展性和持久存储能力而闻名。

##### 1、消息生产

###### 生产者 producer

- 定义

  :

  - 生产者是指在Kafka中负责创建并发送消息到Kafka主题的应用程序或服务。

- 功能

  :

  - 生产者将数据发送到指定的主题，可选择将数据发送到主题的特定分区。

##### 2、消息存储

###### 主题 topic

- **定义**:主题是Kafka中用于存储一组特定类型数据的类别或者名字。
- **特点**:数据被发布到特定的主题，并且消费者可以订阅一个或多个主题来获取数据。

###### 分区 partition

- **定义**:分区是主题的子集，每个主题可以分为多个分区，每个分区是一个有序的、不可变的消息序列。
- **特点**:分区使得Kafka能够在多个服务器上分布式地存储数据，提供了数据冗余和伸缩性。

###### 节点 broker

- **定义**:在Kafka集群中，每个服务器被称为一个broker。Broker负责维护发布到其存储的主题的数据。
- **功能**:Broker处理客户端的请求（生产者和消费者的请求）并存储数据。

###### 消息 message

- **定义**:消息是Kafka处理的基本单位，由一个可选的键（key）和一个值（value）组成。
- **特点**:消息可以是任何类型的数据，如字符串、数字或复杂对象。

###### 副本 replica

- **定义**:为了提高可靠性，每个分区可以在多个Broker上有多个副本。
- **特点**:副本机制确保了即使在Broker故障的情况下数据也不会丢失。

##### 3、消息消费

###### 消费者 consumer

- **定义**:消费者是指从Kafka主题中读取数据的应用程序或服务。
- **功能**:消费者可以订阅一个或多个主题，并从中读取数据。

###### 消费者组 consumer group

- **定义**:消费者组由一组消费者组成，这些消费者共同读取一个主题的数据。
- **特点**:每个分区只能被消费者组中的一个消费者读取，从而在消费者之间提供了负载均衡。

#### 消息分区

##### 1、水平扩缩容

- **概述**Kafka通过分区来实现主题的水平扩展。每个主题可以分成多个分区，这些分区可以分布在不同的Kafka Broker上。

- **优势**

  - **扩展性**:增加分区数量可以提高主题的容量和吞吐量，因为可以并行处理更多的消息。

  - **灵活性**:分区数量可以根据需求调整，以适应不同的负载和存储需求。

##### 2、负载均衡

- **概述**在Kafka集群中，分区被均匀地分配到不同的Broker上，实现了数据和负载的均衡分布。

- **优势**

  - **高效率**:分区允许多个消费者并行读取数据，提高了整体的数据处理能力。

  - **高可用性**:如果某个Broker失败，其上的分区可以由其他Broker上的副本接管，保证了服务的可用性。

##### 3、分区策略：随机/轮询/hash等

- **常见策略**

  - **随机分区**:消息被随机分配到各个分区。适用于不需要特定顺序的场景。

  - **轮询分区**:消息按顺序轮流分配到每个分区。保证了负载的均衡分布。

  - **基于Key的Hash分区**:如果消息具有Key，则根据Key的哈希值分配到特定的分区。这保证了相同Key的消息总是分到同一个分区，从而保证了顺序性。

- **选择策略**

  - 分区策略的选择取决于应用的具体需求，如消息顺序、负载均衡和数据局部性等。

  - 在需要保持消息顺序的场景中，通常使用基于Key的Hash分区。

#### 消息可靠传输

##### 1、顺序消费，消息丢失，重复消费

- **顺序消费**:
  - 确保消息按照产生的顺序进行消费。在Kafka中，分区内的消息是有序的。
- **消息丢失**:
  - 通常由于网络问题、服务器故障等原因导致。需要确保消息队列的持久化和高可用性设置。
- **重复消费**:
  - 可能由于消息重传、消费者重启等原因导致。需要在应用层面处理重复消息。

##### 2、发送方

###### 确认，重试，同步/异步

- **确认（Acknowledgments）**:
  - 发送者可以要求消息队列返回确认，以确保消息被正确接收。
- **重试（Retries）**:
  - 如果消息发送失败，发送方可以选择重试。
- **同步/异步**:
  - 发送消息时可以选择同步或异步方式。同步发送等待确认，异步发送不等待。

##### 3、存储方

###### 持久化策略，replica副本，写入时机

- **持久化策略**:
  - 消息存储在磁盘上以保证持久性。
- **副本（Replicas）**:
  - Kafka通过在多个节点上复制每个分区的数据来保证高可用性和数据安全。
- **写入时机**:
  - Kafka允许配置数据写入磁盘的时机，例如立即写入或周期性刷新。

##### 4、消费方

###### 手动/自动位移提交，同步/异步消费

- **位移提交（Offset Committing）**:
  - 消费者读取消息后，需要提交已消费消息的偏移量。可以手动或自动提交。
- **同步/异步消费**:
  - 消费消息时可以同步或异步处理消息。

###### 分区消费策略

在消费者组内部，需要合理分配分区以实现负载均衡。

###### 消费者组，消息重平衡

- **消费者组（Consumer Groups）**:
  - 多个消费者作为一个组协同消费主题中的消息。
- **消息重平衡（Rebalancing）**:
  - 消费者组成员变化或分区数变化时，会触发重平衡，重新分配分区给消费者。

#### 了解重要配置参数，asks/retries/auto.commit/auto.offset.reset

- **acks（确认）**

  - **作用**:acks 参数用于设置生产者接收消息确认的级别，以确保消息可靠性。

  - **配置选项**:
    - **acks=0**: 生产者不等待来自broker的任何确认。这种配置提供了最高的吞吐量，但最容易丢失消息。
    - **acks=1**: 只要集群的首领节点收到消息，生产者就会收到一个成功响应。这种配置提供了良好的吞吐量和中等程度的数据可靠性。
    - **acks=all或acks=-1**: 生产者会等待所有同步的副本都确认消息。这提供了最高的数据可靠性，但会降低吞吐量。

- retries（重试次数）

  - **作用**:
    - retries配置定义了生产者在发送消息失败时重试的次数。

  - **注意事项**:
    - 如果设置了重试次数，应确保max.in.flight.requests.per.connection（最大未确认请求数）设置为1，以避免消息重排序。

- **auto.commit（自动提交偏移量）**

  - **作用**:
    - 在消费者端，auto.commit 配置用于控制是否自动提交偏移量。

  - **配置选项**:
    - **auto.commit=true**: 消费者会定期自动提交读取的偏移量。
    - **auto.commit=false**: 禁用自动提交偏移量，通常在需要精确控制处理进度时使用。

- **auto.offset.reset（自动偏移重置）**

  - **作用**:
    - auto.offset.reset 配置告诉Kafka消费者在没有初始偏移量或偏移量无效时如何处理。

  - **配置选项**:
    - **auto.offset.reset=earliest**: 自动将偏移量重置为最早的偏移量。
    - **auto.offset.reset=latest**: 自动将偏移量重置为最新的偏移量。
    - **auto.offset.reset=none**: 如果没有找到消费者组的先前偏移量，就抛出异常。

### rocketmq

#### 核心概念

Apache RocketMQ是一种分布式消息中间件和流处理平台，提供高吞吐量的发布/订阅消息传递服务。

##### 1、消息生产

###### 生产者 producer

##### 生产者（Producer）

- 定义

  :

  - 生产者是消息的发送方。它负责创建消息，并将消息发送到RocketMQ的Broker。

- 特点

  :

  - 生产者可以指定消息发送到特定的主题和队列。

##### 2、消息存储

###### 主题 topic

- **定义**:主题是消息分类的标识，用于区分不同类型的消息。
- **特点**:在生产者发送消息和消费者接收消息时，主题被用来路由消息。

###### 标签 tag

- **定义**:标签是主题下的一个子类别，提供了更细粒度的消息分类。
- **特点**:使用标签可以更灵活地控制消息的过滤和选择。

###### 队列 messageQueue

- **定义**:队列是消息的物理存储单位，每个主题可以分布在多个队列中。
- **特点**:队列机制支持消息的负载均衡和并行处理。

###### 消息 massage

- **定义**:消息是在生产者和消费者之间传递的数据载体。
- **特点**:每条消息包含一个或多个属性，如key、tag等，这些属性可用于消息过滤。

##### 3、消息消费

###### 消费者 consumer

- **定义**:消费者是消息的接收方。它订阅特定的主题，并处理接收到的消息。
- **特点**:消费者可以同步或异步地处理消息，并可以手动或自动确认消息的处理状态。

###### 消费者组 consumer group

- **定义**:消费者组是一组消费者的集合，它们共同订阅一个或多个主题。
- **特点**:消费者组支持对消息的负载均衡和容错处理。

###### 订阅关系 subscription 

- **定义**:订阅关系是消费者订阅主题和标签的方式。
- **特点**:通过设置订阅关系，消费者可以选择性地接收感兴趣的消息。

#### 消息类型

##### 1、Normal 普通消息

- **定义**:普通消息是最基本的消息类型，不提供任何特别的保证，如顺序性或事务性。
- **用途**:适用于大多数标准的消息传递需求，如异步处理、系统解耦等。

##### 2、Delay 定时/延时消息

- **定义**:这种类型的消息允许你延迟消息的投递。也就是说，消息被发送后，并不会立即被消费，而是在设定的延时之后才能被消费。
- **用途**:适用于需要在未来某个时间点处理任务的场景，如定时任务、延迟通知等。

##### 3、FIFO顺序消息

- **定义**:FIFO（First In, First Out）顺序消息保证消息按照发送的顺序进行消费。
- **用途**:适用于需要顺序处理消息的场景，如订单处理、日志记录等。

##### 4、Transaction 事务消息

- **定义**:事务消息允许将消息发送和本地事务操作结合起来，保证它们要么都成功，要么都失败。
- **特点**:消息发送分为两个步骤：首先发送半消息（half message），当本地事务成功时再确认消息，否则回滚。
- **用途**:适用于需要保证消息发送与本地事务一致性的场景，如支付处理、库存管理等。

**注意事项**

- **消息选择**:选择哪种消息类型取决于业务场景的具体需求。
- **可靠性和性能**:不同类型的消息可能对系统的可靠性和性能有不同的影响。
- **实现复杂性**:某些消息类型（如事务消息）可能会增加实现的复杂性。

#### 消费模式

##### 1、广播模式

- **定义**:消息被所有订阅者消费，每个订阅者都会收到消息的一个副本。
- **应用场景**:适用于需要将消息通知给所有订阅者的场景，如通知、报警等。

##### 2、集群模式

- **定义**:消息被消费者组中的一个成员消费，每条消息只会被组中的一个消费者处理。
- **应用场景**:适用于负载均衡场景，可以有效地分散消费压力。

#### 通信方式

##### 1、同步RPC调用

- **定义**
  - **同步RPC（Remote Procedure Call）**调用指的是发送方发出请求后，必须等待接收方响应，才能继续执行后续操作。

- **特点**

  - **阻塞操作**:
    - 调用者在等待响应期间不能进行其他操作，这种方式通常被视为阻塞调用。

  - **直接响应**:
    - 发送方可以直接获得请求的结果，易于理解和实现。

  - **适用场景**:
    - 适用于需要即时响应的场景，如用户请求处理、实时数据查询等。

##### 2、异步通信

- **定义**
  - **异步通信**涉及到发送方发出请求后，无需等待接收方的直接响应，可以继续执行其他操作。

- **特点**

  - **非阻塞操作**:
    - 调用者在发送请求后可以立即执行其他任务，提高了程序的并发性能。
  - **响应处理**:
    - 响应可以在任何时间点被处理，通常通过回调函数、事件监听或消息队列来实现。

  - **适用场景**:
    - 适用于处理时间较长的任务，提高系统吞吐量，如大批量数据处理、长时间运行的任务等。

#### 消息传输模型

##### 1、点对点/队列模型

###### 消费匿名，一对一通信

- **定义**:
  - 在点对点模型中，消息被发送到一个队列，消费者从队列中获取消息进行处理。
- **特点**:
  - 消费者通常匿名，每条消息只被一个消费者接收（一对一通信）。
  - 适用于任务分发和负载均衡场景。

##### 2、发布订阅模型

###### 消费独立，一堆多通信

- **定义**:
  - 在发布订阅模型中，消息被发送到一个主题，所有订阅该主题的消费者都可以接收到消息。
- **特点**:
  - 消费者独立，每条消息可以被多个消费者接收（一对多通信）。
  - 适用于广播通知和多方数据分发。

#### 了解重要配置参数，isOrder/consumerModel/concurrent等

- **isOrder（是否顺序消费）**

  - **用途**:isOrder配置用于指定消息是否需要按照发送顺序进行消费。

  - **配置选项**:
    - **true**: 消息将按照严格的顺序被消费。
    - **false**: 消息消费顺序不作保证，可能并行消费，提高吞吐量。

- **consumerModel（消费模式）**

  - **用途**:consumerModel配置用于确定消费者的工作模式。

  - **配置选项**:
    - **CLUSTERING**: 集群模式，多个消费者共享消息，每条消息只会被集群中的一个消费者处理。
    - **BROADCASTING**: 广播模式，消息会被集群中的所有消费者消费。

- **concurrent（并发处理）**

  - **用途**:concurrent配置用于控制消费者并发处理消息的能力。

  - **配置选项**:可以设置为并发处理消息的线程数或者其他相关参数，以提高消费者处理消息的效率。

- **其他重要配置**

  - **消费者组（Consumer Group）**
    - **用途**:用于组织多个消费者实例，以实现负载均衡和故障转移。

  - **消息重试次数（Max Reconsume Times）**
    - **用途**:设置消息消费失败后的最大重试次数。

  - **消息拉取间隔（Pull Interval）**
    - **用途**:设置消费者从Broker拉取消息的时间间隔。

  - **消息批量大小（Batch Size）**
    - **用途**:设置消费者每次从Broker拉取的消息批量大小。
