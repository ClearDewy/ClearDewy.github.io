# 检索、Agent 与智能系统

Agent 不是一个更长的 prompt，而是一个让模型在状态、工具和反馈中循环的系统。模型负责不确定判断，软件负责协议、状态、权限和可恢复执行。

## 1. 先判断是否需要 Agent

- 规则明确、流程固定：优先确定性程序；
- 需要语言理解但步骤固定：模型调用 + 结构化输出；
- 需要外部知识：增加检索并验证引用；
- 需要根据中间结果选择下一步：才考虑 Agent loop；
- 高风险或不可逆动作：增加明确审批，限制自主范围。

## 2. RAG 是独立的检索系统

RAG 包含文档解析、切块、Embedding、索引、召回、重排、上下文组装、生成和引用。端到端答案错误时，要区分“没召回”“排序错误”“上下文丢失”“模型未遵循证据”。

评测必须同时覆盖检索与生成；只评价最终文风会掩盖证据问题。

## 3. 工具调用是一份协议

工具需要名称、参数 schema、返回结构、错误语义、权限和副作用说明。执行前校验参数，执行后把结果转成受控 observation。外部内容是不可信输入，不能被当作更高优先级指令。

## 4. 状态与记忆

- 上下文窗口：本次推理可见的临时状态；
- 会话状态：多轮任务的显式事实和进度；
- 长期记忆：经过选择、版本化和可删除的持久信息；
- 外部知识：来自文档或数据库的可追溯事实。

“把所有历史塞进 prompt”既不是可靠记忆，也缺少隐私、冲突和过期处理。

重试、超时、幂等、预算、循环上限、取消、checkpoint 和失败恢复都属于 Harness，而不是模型能力。

## 6. 多 Agent

只有任务能真正分解、并行收益高于通信成本、结果可独立验证时，多 Agent 才有价值。共享状态、冲突合并、重复劳动、责任边界和评测通常比“增加角色”更难。

## 7. 可观测性与评测

记录输入版本、模型、prompt、检索结果、工具参数/返回、状态转移、token、延迟、成本和最终结果。trace 用于重放和归因；端到端评测关注任务成功与副作用，而非只看单次回答质量。

## 8. 本章实践

先实现一个只有单工具、显式状态机和固定评测集的任务；加入失败注入、重试与审批；最后才比较 Agent 框架。框架替换后，任务语义和测试应保持稳定。
